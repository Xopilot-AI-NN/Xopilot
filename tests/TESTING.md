# Проверка приложения

Запускайте из корня репозитория:

| Команда | Что проверяет |
|---|---|
| `./scripts/test.sh` | SQLCipher, сервисы, потоки API на локальном тестовом сервере, агента, автоматический профиль и статический рендер |
| `./scripts/test.sh full` | Те же тесты, rustfmt и Clippy без предупреждений |
| `./scripts/test.sh ui` | Реальные клики и ввод в отдельном Linux-окне WebKitGTK |
| `./scripts/test.sh model /путь/gemma-4-E2B-it.litertlm` | Настоящий KV-кеш, память разговора, сброс после правки, агент с файлами и настоящий диалог о Canvas |

Для проверки Gemma в интерфейсе:

```bash
XOPILOT_TEST_MODEL=/путь/gemma-4-E2B-it.litertlm ./scripts/test.sh ui
```

Нужны инструменты разработки из README. Для UI также нужен Node.js и графический Linux-сеанс. На Niri стенд меняет ширину 1000/390 px и сохраняет снимки. Сервисы можно проверять без графики и интернета; подготовка зависимостей Cargo и нативного SDK выполняется заранее.

UI-стенд создаёт отдельную базу и проект. Личные данные не открываются. Результаты, снимки и лог лежат в напечатанном каталоге `/tmp/xopilot-ui-check-*`. При настоящей модели копия весов создаётся в `target/ui-models` на диске: после проверки её можно удалить. Проверка модели не скачивает веса и не вызывает API.

Google и настоящий сервер аккаунтов не тестируются до включения сервера. Linux-стенд не подтверждает работу на Android, GPU и Gemma e4b; отдельные проверки телефона описаны в [ANDROID_DEVICE.md](ANDROID_DEVICE.md). SQLCipher печатает сообщения о неверном ключе в тесте неправильного пароля — это ожидаемая часть проверки, ориентируйтесь на итог Cargo.

В установленное приложение диагностический Unix-сокет не входит. Он существует только в примере `interface_interaction` и доступен внутри отдельного каталога с правами 0700.

В проверке Canvas последовательно задаются приветствие, вопрос о списке документов и просьба создать документ с точным содержимым. Проверяется сама запись в SQLCipher, отсутствие служебного протокола в ответах и счётчик engine: веса должны загрузиться один раз, KV-контекст — переиспользоваться между вопросами. Для известного и неизвестного прогресса есть отдельный SSR-тест.

В `local_canvas_smoke` также проверяется продолжение просьбы о файле через Canvas и «тоже самое». Проверка квитанций не позволяет выдавать типичные заявления о создании за выполненное действие без успешного инструмента; это дополнительная проверка, а не гарантия понимания любого запроса моделью.

После Android-сборки выполните `./scripts/test.sh apk [путь/к/APK]`: проверяются все 64-битные ELF LOAD-сегменты и ZIP-выравнивание на 16 КиБ. Нужны Node.js, unzip, readelf и Android Build Tools (`ANDROID_HOME` или `target/android-toolchain/sdk`).

`./scripts/test.sh bridges` проверяет Android-мост импорта: input появляется после запуска скрипта, ошибка Rust сохраняется, повторная передача не получает лишний ответ от предыдущей попытки. Для этого теста нужен Node.js, телефон не требуется.

## APK на настоящем телефоне

Подключите устройство с USB-отладкой и подтвердите доступ. Запустите `./scripts/test.sh apk`.
Сценарий собирает отдельный debug-пакет `by.xopilot.uitest`, устанавливает его через ADB и очищает данные только этого тестового пакета перед прогоном.

Проверки работают в настоящем Android WebView через DevTools. Общий с Linux модуль проверяет разделы настроек, геометрию окон, имя профиля, черновик и сохранение Canvas. Android-сценарии проверяют Home, Back, уничтожение фонового процесса, восстановление черновика и экранную клавиатуру. JSON-отчёт и снимки сохраняются в `target/android-ui-*`.

Для нескольких подключённых устройств задайте `ANDROID_SERIAL`. Переменная `ADB` позволяет выбрать путь к adb. Скрипт сборки использует `JAVA_HOME`, `ANDROID_HOME` и `ANDROID_NDK_HOME` либо уже подготовленный toolchain в `target/android-toolchain`.

Для проверки только ELF/ZIP-выравнивания используйте `./scripts/test.sh apk-check dist/android.apk`. Этот режим подходит и для CI без телефона.
